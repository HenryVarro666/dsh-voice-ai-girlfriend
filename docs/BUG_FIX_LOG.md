# 中文语音助手 Bug 发现与修复记录

项目中的问题并不都来自模型。有些是前端状态划分错误，有些是音频缓冲丢数据，还有些只是延迟策略的取舍。下面按“用户看到什么 → 如何定位 → 根因 → 修改 → 验证”保存案例，供维护、复盘和技术交流使用。

状态以已有部署和实验记录为准，本次文档整理未重新运行模型。代码仍有未提交改动，因此引用文件和函数，不虚构修复 commit。较早的浏览器验证不代表之后本地维护候选已经完成 GPU 回归。

## B01 新会话第一条回复无声

**发现。** 聊天文字已经出现，bridge 却没有收到任何 TTS 请求。问题发生在合成之前，不能用更换音色或 GPU 加速解决。

**定位。** 插件有防止历史重放的基线。第一版修法只排除 `running` 回答，仍然失败。临时记录聊天快照后发现：新会话第一条回答到达监听器时已经是 `settled`；旧会话的历史则由用户和助手节点成批到达。

**根因。** 旧实现等第一条已完成回答出现才确定历史基线，恰好把用户期待听到的第一条回答划进历史，随后跳过。

**修改。** 在第一个非空聊天快照冻结基线，记录其中已完成助手节点的最大 `anchorSeq`。新会话先出现用户消息，基线为零，后续回答正常朗读；旧会话已加载的回答仍被跳过。

**验证。** 历史记录中新会话首轮在回车后 1.38 和 1.43 秒出声；刷新旧会话不重读。后续回归也确认首轮触发 `/api/tts/stream`。这些是有限浏览器样例，不是稳定延迟分位数。

代码：[reply-listener.tsx](../dsh-plugin/src/client/voice/reply-listener.tsx)，`baselineRef` 与历史基线初始化。

**经验。** “第一次看到”不等于“历史”；需要实际观察宿主的数据到达顺序，不能假设每条回答都先经历可见的运行状态。

## B02 页面加载打开数字人导致无声

**发现。** 未部署 DUIX，却收到 `/api/dh/speak` 请求，普通 TTS 没有执行。bridge 配置原本关闭数字人，打开网页后却变为开启。

**根因。** 浏览器 `localStorage` 没有设置时，旧逻辑按开启处理；组件挂载主动 POST `/api/dh/enable`，服务端再将它写入配置。前端默认值覆盖了服务端的明确选择。另一个问题是切回普通语音时，已有回答会被补读。

**修改。** 初始无设置按关闭处理；页面挂载读取 bridge 状态，只有用户点击才写开关。回复只有在服务端开关开启、DUIX 状态为 `running`、本地选择及展示窗口均允许时才走视频，其余走句子 TTS。进入数字人路径时记录已有回答的处理状态，避免切回后补读。

**验证。** 新浏览器加载没有开关 POST，配置保持关闭；DUIX 不可用时语音路径仍工作，关开关不补读。真实 DUIX 生成尚未验证，替身链路测试不能替代真实视频服务。

代码：[DigitalHumanToggle.tsx](../dsh-plugin/src/client/DigitalHumanToggle.tsx)、[reply-listener.tsx](../dsh-plugin/src/client/voice/reply-listener.tsx)。

**经验。** 读取设置与修改设置应是两个动作；可选服务不可用时，要明确主功能如何继续。

## B03 Markdown 列表被整段合成

**发现。** 一次把 276 字送入 TTS，生成 41.7 秒音频，失去逐句朗读的响应优势。

**根因。** 清洗函数把换行压成空格，切句只认句末标点。没有句号的列表项粘在一起。有序编号也没有被去除。

**修改。** 句子朗读模式保留换行，去掉 `1.`、`1)`、`1、` 等编号；未闭合代码块先隐藏，避免代码生成期间被逐行念出。首段满 5 字可在中文逗号、分号、冒号处提前切；每段最多 60 字，长段优先寻找后半段软断点。DH 和 QQ 保留原来的单行清洗模式。

**验证。** 自动测试覆盖列表清洗、长度上限和流式前缀。现场模型未按测试要求输出 Markdown 列表，因此没有将那次 UI 测试算作列表端到端验证。后续三种首句策略对照未找到一致赢家，保留当前规则，见[首句实验](experiments/2026-10-20-first-clause/RESULTS.md)。

代码：[clean.ts](../dsh-plugin/src/client/voice/clean.ts)、[sentences.ts](../dsh-plugin/src/client/voice/sentences.ts)。

## B04 列表逐字到达时撤回了句子边界

**发现。** 新增的流式前缀回归测试失败：某一时刻已经切出的“先吃饭”，在下一行列表编号继续到达后消失，退回未完成文本。

**根因。** `.trim()` 删除末尾换行；而换行正是切句器已经使用的完成边界。监听器按句子序号记进度，边界反复变化会产生漏读或重复风险。

**修改。** `keepLines` 模式只去开头空白和末尾水平空白，保留末尾换行；普通单行模式仍使用原来的清理方式。两个仓库的源码副本同步。

**验证。** 先记录失败测试，再修改实现，同一测试通过。每次只给输入增加一个字符，检查已经输出的完整句必须保持为新输出的前缀。2026-10-20 部署 bundle 为 `45194657…`；后来本地维护候选已继续变化，不能混称同一版本。

代码：[clean.ts](../dsh-plugin/src/client/voice/clean.ts)。测试位于独立插件仓库 `tests/voice-regression.mjs`。

**经验。** 流式系统不仅要验证完整输入的结果，还要验证中间结果会不会被后续字符推翻。

## B05 静默过久后下一句话被丢弃

**发现。** 开着麦克风静默约 30 秒再说话，STT 返回 422，提示音频长达 31.8 秒。浏览器判定往返很慢，服务端实际推理却只需几十毫秒。

**根因。** 录音器积累了上一句结束后的全部静音，下一句开口时将其一起上传，超过 30 秒限制。

**修改。** 未开始说话时仅滚动保留 0.5 秒预录；开始说话后再累积当前句。这样既保护开头音节，也限制无意义上传。

**验证。** 假麦克风静默超过 3 分钟后再次说话，上传约 2.5 秒，不再报 422。自动测试验证待机缓冲有界。

代码：[recorder.ts](../dsh-plugin/src/client/voice/recorder.ts)，`PRE_ROLL_BYTES`、`trimChunks`。

## B06 插话打断时丢失开头音节

**发现。** 回复播放中说“我想换个话题聊聊”，识别只剩“换个话题聊聊”。没有回复播放时，同一句能完整识别。

**定位。** 记录 VAD 事件和上传长度：silero 需要约 384 ms 人声才确认开始说话，实测通知在开口后约 0.44–0.45 秒到达。

**根因。** 播放期间音频只送 VAD，本地不保留；收到 `speech_start` 后又清空缓冲，检测所需的那段人声随之丢失。

**修改。** 播放期间保留最近 1 秒音频；确认插话后从该缓冲接上后续录音，并立即进入说话状态，避免又被普通 0.5 秒预录规则裁短。RMS 降级路径同样处理；自然播放结束保留 0.5 秒预录。

**验证。** 修复后上述句子完整识别，上传 2.44 秒；“等一下，我还有个问题”也完整识别。使用的是假麦克风，外放漏过 AEC 的回声可能混入这 1 秒，仍需真人验证。

代码：[recorder.ts](../dsh-plugin/src/client/voice/recorder.ts)，`BARGE_IN_KEEP_BYTES`、`onVadSpeechStart`。

## B07 Qwen3 语音模型加载字段不兼容

**发现。** 流式 TTS 原型加载失败：`MimiConfig` 没有 `rope_theta` 属性。

**根因。** Qwen TTS 注册的 RoPE 初始化读取旧配置字段；当前 transformers 5.20 的 Mimi 配置将相应值放在 `rope_parameters` 中。

**修改。** 加载 handler 前执行 `_patch_qwen_tts_rope()`，为缺失旧字段的初始化提供兼容读取。不直接编辑已安装依赖包；旧配置正常时保持原行为。

**验证。** 原型成功加载，之后生产 bridge 的 Qwen3 流式合成也已运行。这里验证的是记录中的具体依赖组合，不承诺兼容所有 transformers 版本。

代码：[voice_bridge.py](../bridge/voice_bridge.py)，`_patch_qwen_tts_rope`。

## 尚未关闭的性能与体验问题

### P01 缩短静音等待有误截断代价

固定等 1.8 秒属于策略，不是单纯代码缺陷。当前实验配置在静音 500 ms 后请求文本说完判定，完整即发送，未完整或仍在等待则到 1.2 秒兜底；接口不可用退回 1.8 秒。用户恢复说话后，旧判定作废；完整判定返回识别文字，避免重复 STT。

历史 FLEURS 真人朗读策略模拟中，平均等待从 1.8 秒降至约 0.89 秒，句中截断从约 1% 升至 9.5%。这是等待与误截断的交换，不能称为全面修复，也不能把朗读语料直接当成真人对话效果。

### P02 同卡争用已量化，调度未修改

正式每组 20 次，LLM 未加载、仅驻留、同时生成时，TTS 首有声 PCM 到达中位数为 184.7、185.2、313.1 ms。并发相对驻留增加约 128 ms；仅驻留仍出现 1906 ms 长尾，说明争用不能解释所有慢请求。

测量从 loopback TTS HTTP 请求计到首有声块到达，不含整条语音对话。尚未实现 GPU 调度修复。[协议与结果](experiments/2026-10-20-tts-contention/RESULTS.md)。

### P03 前导静音生成机制已复现，未消除

隔离测试中 seed16 原始首块约 98 ms，但模型先生成约 4.584 秒静音，handler 到约 1217 ms 才交出 PCM；同 seed 重放约 1219 ms。说明“原始首块很快”不等于“用户很快听见声音”。这只是复现的一种机制，不能反推旧 1906 ms 请求必然同因。

没有采用固定好 seed 或删除慢样本来冒充修复。[追踪结果](experiments/2026-10-20-tts-tail/RESULTS.md)。

### P04 段尾保护已有实验原型

部分生成音频末尾存在约 5 秒连续低幅度区。离线候选仅处理长于 1 秒、幅度低于 0.003 的末尾区域，保留 300 ms，不动开头和句中。四段样例删除约 5.1–5.3 秒，保留的 PCM 前缀不变，裁剪后 ASR 均匹配。

后续已实现未启用的 `bridge/stream_tail.py`，v2 先放行 300 ms 余量，有界缓存 256000 字节，正常EOF裁剪，取消丢弃，超限放行。14 项契约覆盖句中停顿、边界与取消等；旧数据和新模型输出重放未新增估算欠载或推迟首声。[流式实验结果](experiments/2026-10-20-stream-guard/RESULTS.md)。

ASR 匹配不等于听感无损，低幅度也不必然是静音。测试明确保留了低于阈值的真实尾词会被误裁的反例，因此未接入生产，需要回听及实际播放器验证。[离线裁剪结果](experiments/2026-10-20-tts-tail/RESULTS.md)和重放估算都不应写成生产延迟已降低约 5 秒。

2026-10-20 追加[严格尾部保护验证](experiments/2026-10-20-tail-safety/RESULTS.md)：已实现未启用的数字零与异步保护器。受控弱声非零样本完整、慢流和HTTP取消测试通过，但241段归档真实尾部零裁剪。旧幅度规则仍误裁弱声，故不部署；天然轻声和浏览器插话未重新验收。

2026-10-20 追加[生成端对照](experiments/2026-10-20-generation-end/RESULTS.md)：已知seed25默认自然EOS而非撞上限。重复惩罚1.05→1.15将其尾部5355.5→79.1ms、帧113→23；seed16前导也缩短。诊断后新文本各12条没有整体首声收益，ASR各9/12，一改善一退化，尚未回听。降低温度有1条撞上限。P03/P04仍是未上线修复，生成参数候选不等于可靠解决。

2026-10-20继续[1.15扩展108条验证](experiments/2026-10-20-repetition-validation/RESULTS.md)：本组首有声中位183.0→100.5ms，两边无超过1秒尾部、均自然EOS。ASR各47/54，但自然结尾组18/18→17/18，“好了/好啦”待回听；54对已整理，优先8对。P03/P04仍未上线修复，不能以总分相同推断轻声安全。

2026-10-20追加[生成布局正式80条](experiments/2026-10-20-generation-layout/RESULTS.md)：chunk2与默认20对声学码全同，长静音不变；逐步文本seed16仍有4.573秒前导并增加1.780秒尾部。仅向量把seed25尾部5355.5→83.4ms，新文本首有声中位143.0→92.2ms，但克隆条件和韵律改变，未听检或部署。受并行GPU干扰首轮另存，不用于正式计时。两轮音频80/80逐字节一致而一条ASR变化，同PCM重查有0/0/2编辑，记录为未定位的检查器波动，不把它直接认定为新TTS吞字。P03/P04仍未上线修复，裁剪继续关闭。

2026-10-20新增[数字规范化独立对照](experiments/2026-10-20-number-reading/RESULTS.md)：编号匹配12/24→23/24，但新5.413秒段尾与单次少位疑点仍在，未部署。另修实验核对器未知字符被截成前缀的问题：新增先失败后通过契约，原始数据不覆盖，CPU完整字段重算；该修正只涉及实验统计，不是生产语音修复。

每个新案例追加稳定编号，保留以下信息：

1. 触发条件和用户可见症状，最好有修复前的失败样例。
2. 用什么日志或对照排除了哪些假设；失败的第一版修法也保留。
3. 根因所在边界、修改文件和关键行为变化。
4. 相同输入下修复后的证据，以及回归测试命令或结果文件。
5. 是否部署、对应构建或 commit、仍未覆盖的场景。

修复、诊断和优化实验分别标状态。回归统计随版本记录；合成输入、真人录音、假麦克风与现场外放不能互相替代。不要把令牌、密码、个人参考音频或未经授权的录音写入案例。
