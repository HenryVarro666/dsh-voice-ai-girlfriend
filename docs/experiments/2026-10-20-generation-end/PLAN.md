# 生成端结束与静音长尾小实验

2026-10-20，正式运行前冻结。只在apex独立进程加载生产同款0.6B模型，不替换服务、配置、安装包或插件；不使用幅度裁剪，不缩短输出token上限。

## 依据与假设

本机安装的faster-qwen3-tts 0.5.4在第一码本采样到 `codec_eos_token_id` 时结束；音频流 `is_final` 只是分块信息，不能代替EOS证明。speech-to-speech 0.2.10的CUDA克隆路径没有把通用 `gen_kwargs` 传给生成方法，实验须显式改变模型调用参数，记录实参，避免只改配置却未生效。

官方[EOS问题报告](https://github.com/QwenLM/Qwen3-TTS/issues/118)描述过跑到token上限的情况，但不能直接认定本项目seed25同因。[加速库方法](https://github.com/andimarafioti/faster-qwen3-tts/blob/main/faster_qwen3_tts/model.py)支持采样温度、重复惩罚；以apex安装文件哈希为本实验实际实现。

假设：有些长尾是EOS概率/采样路径问题，可通过生成参数减少；也可能EOS正常、只是EOS之前模型已经生成过长静音。用逐步EOS记录区分，不把波形裁剪当成生成修复。

## 冻结对照

诊断组：沿用既有四条TEXTS，seed0/16/25，各策略12条，合计48条，任务交错随机顺序（seed20261020）。

1. 原默认：temperature0.9、repetition_penalty1.05、top_k50、top_p1.0、do_sample=true。
2. 降温：仅temperature改0.5。
3. 重复惩罚：仅repetition_penalty改1.15。
4. EOS偏置：仅对第一码本EOS logit加1.0，其余采样规则不变；这是有提前结束风险的实验对照，不称为安全停止器。

min_new_tokens、max_new_tokens、chunk_size、音色和参考音频与生产handler相同。最短token规则仍由库执行，不强行按文本长度切音频，不选择固定“好seed”。先额外跑同一已知seed16/25的无EOS追踪基线各一次，估计记录开销，不计正式组。

诊断后只允许选一个候选继续：必须全部自然EOS、总转写字符编辑距离不高于基线，按“超过1秒尾部的数量、尾部总时长”字典序优于基线；若多候选合格按相同排序、再以温度/惩罚/EOS偏置顺序打破相同结果。没有合格候选则不再扩样。

独立验证组冻结四条新文本、seed606/707/808，候选与默认各12条：

- 今天先休息吧，明天再继续。
- 你说的是星期四上午九点吗？
- 我想确认一下，最后一个字是轻声的呢。
- 请先保存文件，等检查完成以后，再关闭窗口。

文本和seed不按诊断表现修改。诊断与验证分开报告，少量样本不推断稳定p95或错误概率。

## 记录与验收

- 在独立进程包装第一码本采样函数，记录每步EOS采样概率（含mask、温度、top-k后）、EOS排名、是否采样EOS；不改上游安装文件。不公开完整声学token或参考素材。
- 每条记录实际生成帧数、采样步数、自然EOS/上限/其他原因、上限值；原始生成音频与handler PCM分别测首声、前导/尾部低幅度时长。幅度只用于测量，不裁波形。
- 每条输出用现有FunASR检查，统计包含失败在内的字符编辑距离和结尾差异，不把同音字自动认定为TTS错误，也不把ASR一致当成音色/韵律无损。音频留apex供回听。
- 记录模型加载、每条生成总时间和资源；追踪增加开销，因此计时只作同条件诊断。EOS偏置即使ASR通过仍需人工回听与独立验证，不能因停止更早就部署。
- 启动要求空闲显存至少9000MiB、GPU利用率不高于20%、Ollama无加载模型；加载后不足1500MiB则只结束自有进程。结束释放模型，核对生产哈希、health和其他进程。

## 停止规则

任何策略出现无法加载、OOM、空输出或上限截断都保留失败记录，不调参数重跑覆盖。若没有同时改善长尾和内容完整性的候选，报告否定结果。生产不部署；参考音频/人声不进入公开仓库，结果写回项目状态、Bug记录和双语入口。
